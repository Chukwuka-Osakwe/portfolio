When someone hands you a solution disguised as a request — *make it bigger*,
*add a tab*, *put it on the homepage* — they've already done the diagnosis for
you. That's the trap. The request encodes an assumption about cause, and the
assumption is usually wrong.

## Two questions before any pixel

I try to ask two things before opening the canvas:

- **What did you observe** that made you ask for this?
- **What would have to be true** for this to be the right fix?

The first surfaces the symptom. The second exposes the leap.

## Why this matters

Designing to the stated problem feels productive — you ship something, fast.
But you spend credibility on a fix that doesn't move the number, and the next
request lands with the same buried assumption. Designing to the *real* problem
is slower to start and far cheaper over time.

This is the throughline in most of my [work](/work): the interesting move is
almost always upstream of the request.
